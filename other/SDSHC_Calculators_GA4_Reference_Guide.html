🌷Property Setup

One GA4 property holds both calculators, as two web data streams. Custom dimensions are registered at the property level, so every dimension in this guide is registered once and works for both sites.

SiteURLStreamMeasurement ID
Grazing Calculator plantshley.github.io/SDSHC-grazing-calculator/ Grazing Calculator G-4HVP5HPZG4
Farm Plan Budget plantshley.github.io/SDSHC-farm-budget/ Farm Plan Budget G-H3X4G4WPYH

Why the shared hostname does not conflate anything

Both sites live on plantshley.github.io, along with every other GitHub Pages repo on that account. None of those others is tagged, so none of them sends anything. The Measurement ID is the filter, not the stream URL. The URL typed into GA is a label only.

The SDSHC Games Hub has been running G-P08D60FD2Y on the same hostname in its own separate property for months, which is the working proof.

Cookies are shared, data is not. Because github.io is on the browsers' Public Suffix List, the _ga cookie lands on plantshley.github.io and is shared across every path there. A producer who uses both calculators therefore counts as one person in this property rather than two, which is exactly what one property with two streams is for. Do not set a cookie_path to isolate them: it would split that producer in half and break the combined count.

Property settings that matter

  • Data retention: 14 months. GA defaults to 2 and it is not retroactive. Already set.
  • Google Signals: leave off. Off by default in a new property. It powers ads remarketing and demographics, neither of which these tools need, and switching it on triggers data thresholding that hides report rows at low traffic.
  • Timezone Central, currency USD.
  • Enhanced measurement: on. Only three of its seven options can ever fire here. See Known Limits.

💐Sample Queries You Can Run

Most of these live in Explore → Free form. Add the dimension on the left, the metric Event count or Total users in the middle, and a filter on Event name.

Which grazing worksheet gets used more?
Event name = worksheet_start
Dimension: worksheet
Metric: Event count
Where do people give up on a worksheet?
Event name = step_advance
Dimension: step, secondary worksheet
Metric: Total users
Read the drop between step 2 and step 3, not the raw counts.
What fraction of starts actually finish?
Compare Total users on worksheet_start against results_complete, split by worksheet.
Or build it as an Exploration → Funnel with those two steps.
Which terms confuse people?
Event name = definition_open
Dimension: definition_id
Metric: Event count
The most actionable report in either property. It tells you what to reword in the app AND on the printed worksheet.
Do producers pick one forage type or "mixed"?
Event name = results_complete
Dimension: forage_type
Metric: Event count
What are producers actually calculating for?
Event name = results_complete
Dimension: goals
Metric: Event count
Seven possible values. For a per-goal total instead, filter goals contains days.
Which entry mode do people prefer?
Event name = mode_select
Dimension: control, secondary choice
Metric: Event count
One report covers every segmented control in both apps: dry matter, frame size, occupation period, cost line mode, yield unit, and the two basis pickers.
Did anyone need more than four enterprises?
Event name = enterprise_added
Dimension: count
Metric: Event count
The spreadsheet capped at four. Anything above 4 here is the app earning its keep.
Are the typical values any good?
Compare Event count on typical_value_open against typical_value_applied, split by typical_key.
A key with many opens and few applies is a shipped figure that does not match real operations. That is a data problem worth fixing in data/typical-values.js.
Do the forage photos earn their install size?
Event name = photo_open
Dimension: set
Metric: Total users
The images are precached, so they are the app's offline install weight. If nobody opens them, that budget is buying nothing.
How many people install it as an app?
Dimension: display_mode (user-scoped)
Metric: Total users
Plus the pwa_installed event for the moment of installing.
Does anyone use the mono font or dark theme?
Dimension: font or theme (user-scoped)
Metric: Total users
Do not use theme_change / font_change to answer that last one. Those events only fire when somebody touches the control. A producer who set mono six months ago and has been happy ever since fires nothing, so the change events would show mono as near-dead however popular it is. That is why theme and font are also sent as user properties on every load. Use the user properties for proportions and the events for "does anyone go looking for the setting".

💾export_file BOTH

Every download and every print. This has to be tracked by hand. Both apps download through URL.createObjectURL(), and GA4's automatic file_download only matches file extensions in an href, so it never sees a blob.

formatpng, csv, json, print
scopeworking (the thing on screen), saved (from a card), backup (everything at once), compare (budget only)

⚠️warning_shown BOTH

A plausibility warning appeared. Fires once per warning per calculation, not once per keystroke.

warning_idA slug of the warning's first six words, e.g. animal-weight-cannot-be-below-zero.
Rewording a warning starts a new dimension value. Both models raise warnings as finished sentences, and the flat list is what the CSV and the share image carry, so there is no id to send. The slug is derived from the sentence itself. If you change a warning's opening words, the old value stops accruing and a new one begins. Nothing errors and nothing warns you. Giving warnings real ids would mean changing what warnings holds, which every consumer reads.

📚guide_open BOTH

sourcefooter or step

🎨theme_change & font_change BOTH

choicetheme: light, dark. font: browser, classic, mono. Always the resolved value, so an unset theme reports what the system gave it rather than a blank.

📱pwa_installed BOTH

Fired off the browser's appinstalled event. No parameters.

📥backup_restored & calc_imported / scenario_imported BOTH

A file was read back in. No parameters beyond worksheet in the grazing calculator.

🌾Grazing Calculator Only

🚜worksheet_start

Start or Return pressed on a setup screen.

worksheetperennial or covercrop
goalsSorted and comma-joined, e.g. acres,days. Seven possible values.
forage_typePerennial only. A forage key, or mixed.
seasonCover crop only. The season key.

➡️step_advance

Moving forward through the worksheet, and only forward.

worksheetperennial or covercrop
step1 to 5. One-based, matching what the stepper says on screen.
methodnext (the Next button) or stepper (a circle in the strip). Tells you whether the stepper is used at all.
Going back is deliberately not counted. Returning to step 2 to check a figure is what the stepper is for, and counting it would inflate the funnel with the same step twice. Moves blocked by the speed bump in mayLeaveStep() are not counted either, since they never happened.

✅results_complete

Every selected goal has an answer. Fires once per calculation. Same parameters as worksheet_start, so the two make a two-step funnel.

🏷️calc_saved

A calculation was written to the Saved list. Fired from the dialog's apply callback, not the Save button, because that dialog can be cancelled.

first_saveyes on a first save, no when "Edit saved" rewrites the figures.
worksheetPlus goals, forage_type or season.

📷photo_open

setWhich viewer set: the forage chart, the growth stage photos, or the cover crop seasons.

📋show_all_steps

stateon or off. Says whether the whole-sheet mode is worth maintaining.

💵Farm Plan Budget Only

🆕scenario_start

A new budget was begun. No parameters.

✅budget_complete

Revenue and cost are both above zero, so the profit line means something. Fires once per scenario.

enterprisesHow many enterprises the budget holds.
This one is a judgement call. The budget has no unanswered-goal concept the way the grazing calculator does, so "complete" had to be defined. Revenue alone is half a budget, and its profit line is just the revenue over again, which is why both sides are required. Treat it as a good proxy rather than a hard fact.

🌱enterprise_added

countHow many enterprises the budget now has, counted after the row lands.

The spreadsheet capped at four enterprises and removing that cap is a stated reason this app exists. This is the figure that judges the decision.

⚖️compare_run

countHow many budgets were compared. Never below 2, since the app refuses fewer.

📊typical_value_open & typical_value_applied

The picker was opened, and separately, a figure from it was actually written into a box. The gap between the two is the number worth having. Somebody who opens the picker and closes it again is telling you the shipped figure did not fit their operation, which is a different and more useful signal than "nobody uses typical values".

typical_keyWhich figure, e.g. seedsPerBag, usefulLifeEquipment.
categoryThe picker's category filter, when it has one.

🗂️folder_created & scenario_saved

enterprisesOn scenario_saved: how many the budget holds.
first_saveyes or no. Fired only after the save succeeds, so a conflict prompt that was cancelled does not count.

🎀How to Register a Custom Dimension

  1. Open Admin (the gear icon).
  2. Under Data display, choose Custom definitions.
  3. Create custom dimension.
  4. Dimension name: what you want to see in reports, e.g. "Worksheet". This is a label and can be changed later.
  5. Scope: Event for everything except theme, font, and display_mode, which are User.
  6. Event parameter (or User property): the exact name from the tables above, lowercase, spelled precisely. A typo here produces a dimension that silently stays empty forever.
  7. Save. Data begins accruing from now, never backwards.
Give it 24 to 48 hours before judging it. A newly registered dimension often shows (not set) at first while GA catches up. For an immediate check, use Admin → DebugView with the site open, or the Realtime report.

The four rules the module lives by

  1. Nothing a producer typed ever leaves the device. Only structure goes out. No dollar figures, no crop names, no pasture names, no saved records.
  2. It never throws and never blocks. Every entry point is wrapped in try/catch. Analytics that can break the calculator is worse than no analytics.
  3. Production on the real host only. npm run dev and local previews send nothing.
  4. calc.js never learns the module exists. Both models stay pure.

Turning off your own traffic

Visit either live site once with ?noga=1 on the end:

https://plantshley.github.io/SDSHC-grazing-calculator/?noga=1
https://plantshley.github.io/SDSHC-farm-budget/?noga=1

That browser stops reporting for good. ?noga=0 turns it back on. Each site has its own flag, so do both, and do it on every browser and phone you test with.

This is used instead of a GA internal-traffic IP filter because a residential IP is dynamic and does not cover a phone on cell data, so an IP filter goes stale silently. At twenty real users a month, fifteen deploy checks would otherwise be nearly half the data.

Checking a call site is wired, without polluting the reports

Run npm run dev and open the browser console. In development the module sets window.__gaDebug and logs every call as [ga] event_name {params} without sending anything.

Privacy copy

Three places in each app carry the promise and they move together: the footer sentence, the privacy definition, and the how-to's saving section. All six were narrowed when this landed, from "Everything you enter stays on this device" to "Your figures stay on this device", plus a sentence naming what is counted. The old wording would no longer have been true, because the worksheet you open and the options you pick are now sent.

🚧Known Limits

Offline sessions record nothing at all. gtag.js is cross-origin and is deliberately not precached by either service worker. This matters most for the Farm Plan Budget, whose users are producers and students, at the Soil Health School or at home, on phones or laptops, potentially with no signal. A workshop room with poor reception can register as almost no traffic. Do not read a quiet week as nobody using it.
  • Ad blockers eat 10 to 30% of GA traffic. Every number in these reports is a floor, not a count.
  • Only three enhanced measurement options can ever fire. Page views, scrolls, and outbound clicks. Site search needs URL query parameters neither app uses. Video engagement needs embedded video. Form interactions need <form> elements, and neither app has a single one. File downloads cannot see a blob URL. The inactive ones are harmless, so they are left on.
  • Outbound clicks are worth watching in the grazing calculator. The one external link is SDSHC's older JotForm version of the cover crop worksheet, on the cover crop setup screen. Clicks on it say people still prefer the old online form.
  • Neither app touches the History API, so GA's automatic page_view fires once per load and never again. Every move within a session is an explicit event. Do not expect page-path reports to show anything beyond the two entry URLs.
  • Rewording a warning starts a new warning_id. See the warning_shown section above.
  • budget_complete is a defined proxy, not a fact. See its section above.
